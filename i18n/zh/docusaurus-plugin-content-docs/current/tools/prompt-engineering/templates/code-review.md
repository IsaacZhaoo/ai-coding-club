## 1) PR 审查（bug + 测试 + 风险）

```text
你是一名资深工程师，请做代码审查。

输入：
- 目标： [GOAL]
- 已验证方式： [COMMANDS]
- Diff（或变更文件）：
[粘贴 DIFF]

输出：
- 按严重程度排序的问题清单
- 缺失的测试
- 潜在回归点
- 建议的后续动作
```

AI 审查会输出一份结构化反馈：需要把报告中的文件名、行号和代码段与你的本地仓库及最新 diff 逐项核对。对于每一项问题，用可复现的方式描述触发条件（输入数据、调用路径或并发场景），并说明下游系统或终端用户可能观察到的影响；若缺少必要上下文，明确标注为“待确认”。

记住：AI 的反馈是建议与线索，不是最终验收依据。你需要区分三类内容——已验证的检查与结果、建议补充的测试覆盖，以及尚未通过代码或实验确认的判断。想系统了解目标、调用链、验证质量与风险边界的完整工作流，请阅读 [AI Code Review 工作流程](/zh/docs/tutorials/ai-code-review-workflow/)。

## FAQ

### 提供什么材料能得到更好的审查？

给 diff/变更文件 + 目标 + 已验证方式。

### 如何减少泛泛而谈？

要求按严重程度排序，并给出文件/行号级别的问题与建议。

### 审查必须覆盖什么？

行为回归风险、安全问题与缺失测试。
