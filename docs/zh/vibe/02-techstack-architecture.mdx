# 技术选型与架构设计

> 让 AI 成为你的架构师,构建坚实的技术基础

完成本节后,你将掌握如何让 AI 推荐技术栈、理解现代 BaaS 方案的优势,以及如何准备核心上下文文档。

## 一、技术选型: 让 AI 成为架构师

### 1.1 为什么技术选型如此重要?

**类比**: 技术栈 = 建筑材料
- 用错材料 → 性能瓶颈或成本过高
- 选对技术 → 开发效率提升 10 倍

**影响因素**:
- 开发效率 (Time to Market)
- 长期维护成本
- 可扩展性

### 1.2 AI 架构师提示词

```
你是一位经验丰富的解决方案架构师,擅长为独立开发者设计技术方案。
核心原则:在保证系统健壮性和可扩展性的前提下,最大化开发效率、最小化运维成本。

这是我的产品 PRD:
[粘贴完整 PRD]

请推荐 2-3 套技术栈组合(前端+后端+数据库+部署),并从以下维度分析:
• 开发效率
• 维护成本
• 可扩展性
• 学习曲线
• 社区生态

最后推荐一个最适合的方案,并说明理由。
```

### 1.3 典型方案对比

| 方案 | 技术栈 | 优势 | 适合场景 |
|------|--------|------|----------|
| **经典全栈** | Next.js + Node.js + MongoDB + AWS | 灵活,成熟 | 大团队,复杂业务 |
| **现代 BaaS** | Next.js + Supabase + Vercel | 极快开发,运维简单 | **独立开发,快速迭代** ⭐ |
| **传统企业** | Spring Boot + MySQL + 自部署 | 控制力强 | 企业级项目 |

## 二、推荐方案: Supabase + TypeScript + Vercel

### 2.1 为什么选择这套组合?

**三大优势**:

1. **开发效率极致**
   - Supabase 提供开箱即用的后端服务
   - 从创意到上线只需 2-4 周

2. **运维成本极低**
   - 免费额度足够 MVP
   - 无需专职运维
   - 自动扩容

3. **质量不妥协**
   - TypeScript 保证代码质量
   - 企业级安全 (RLS)
   - 可扩展至百万用户

### 2.2 技术栈详解

#### Supabase: 后端瑞士军刀

**核心功能**:
- PostgreSQL 数据库
- 用户认证系统
- 文件存储
- 实时订阅
- Serverless 函数

**示例对比**:
```typescript
// 传统方式: 50+ 行代码
// Supabase: 3 行搞定
const { data, error } = await supabase.auth.signUp({
  email: 'user@example.com',
  password: 'secure123'
})
```

#### TypeScript + Next.js: 现代前端

**TypeScript 价值**:
- 编译期发现 80% 错误
- IDE 智能提示
- 重构更安全

**Next.js 优势**:
- 文件式路由
- 服务端渲染 (SEO 友好)
- API Routes

#### Vercel: 零配置部署

**一键部署**:
1. 推送代码到 GitHub
2. Vercel 自动构建
3. 2 分钟后上线,HTTPS 域名

## 三、核心上下文文档准备

### 3.1 为什么需要这些文档?

**类比**: 上下文文档 = 施工图
- 没有施工图 → AI 只能瞎猜
- 有了施工图 → AI 精确执行

**四大核心文档**:
1. `PRD.md` - 产品需求 (已完成)
2. `schema.sql` - 数据库结构
3. `rls.sql` - 安全策略
4. `api.md` - 接口设计

### 3.2 设计数据库结构 (schema.sql)

**步骤 1: AI 生成初稿**

```
基于这份 PRD [粘贴],设计符合第三范式的 PostgreSQL 表结构。

要求:
1. 使用 SQL DDL 语法
2. 为关键字段添加注释
3. 说明表关系
4. 考虑扩展性
```

**步骤 2: 示例输出**

```sql
-- 用户表
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email TEXT UNIQUE NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 播客总结表
CREATE TABLE summaries (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES users(id) ON DELETE CASCADE,
  podcast_url TEXT NOT NULL,
  title TEXT NOT NULL,
  summary_text TEXT,
  transcript TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW(),

  -- 性能优化索引
  INDEX idx_user_summaries ON summaries(user_id, created_at DESC)
);
```

**步骤 3: 交叉验证**

```
请以数据库专家身份审查这份 schema:
[粘贴 schema]

关注:
1. 是否有冗余字段?
2. 索引设计是否合理?
3. 字段类型是否最优?
```

### 3.3 定义行级安全策略 (rls.sql)

**RLS 是什么?**
Row-Level Security = 数据库级别的权限控制,比应用层更安全。

**提示词**:
```
基于 PRD 和 schema,为每张表设计 RLS 策略。

规则:
- 用户只能访问自己的数据
- 未登录用户只能读公开内容
```

**示例策略**:

```sql
ALTER TABLE summaries ENABLE ROW LEVEL SECURITY;

-- 用户只能查看自己的总结
CREATE POLICY "Users can view own summaries"
  ON summaries FOR SELECT
  USING (auth.uid() = user_id);

-- 用户只能插入自己的数据
CREATE POLICY "Users can insert own summaries"
  ON summaries FOR INSERT
  WITH CHECK (auth.uid() = user_id);

-- 用户只能删除自己的总结
CREATE POLICY "Users can delete own summaries"
  ON summaries FOR DELETE
  USING (auth.uid() = user_id);
```

### 3.4 设计 API 端点 (api.md)

**提示词**:
```
根据 PRD、schema 和 rls,设计 RESTful API。

格式要求:
1. Markdown 表格
2. 包含: HTTP 方法、URL、功能
3. 提供请求/响应示例
```

**示例输出**:

```markdown
## API 端点设计

### 用户认证

| 方法 | 端点 | 功能 | 请求体 | 响应体 |
|------|------|------|--------|--------|
| POST | `/api/auth/signup` | 用户注册 | `{ "email": "...", "password": "..." }` | `{ "user": {...}, "session": {...} }` |
| POST | `/api/auth/login` | 用户登录 | 同上 | 同上 |

### 播客总结

| 方法 | 端点 | 功能 | 请求体 | 响应体 |
|------|------|------|--------|--------|
| POST | `/api/summaries` | 创建总结 | `{ "podcast_url": "..." }` | `{ "id": "...", "status": "processing" }` |
| GET | `/api/summaries/:id` | 获取详情 | - | `{ "title": "...", "summary": [...] }` |
| DELETE | `/api/summaries/:id` | 删除总结 | - | `{ "success": true }` |
```

### 3.5 文件组织

```
your-project/

│   ├── PRD.md
│   ├── schema.sql
│   ├── rls.sql
│   └── api.md
├── src/

```

**提示词**:

## 五、普适的"道"与"术"

### 从 Supabase 到通用思维

| Supabase 的"术" | 普适的"道" | 核心问题 |
|----------------|-----------|----------|
| schema.sql | 数据模型定义 | 要处理什么数据? |
| rls.sql | 访问控制逻辑 | 谁能访问哪些数据? |
| api.md | 应用接口契约 | 系统如何通信? |

**其他技术栈参考**:

**Django + MySQL**:
- 数据模型 → `models.py`
- 访问控制 → Django Permissions
- API → Django REST Framework

**Spring Boot**:
- 数据模型 → JPA Entities
- 访问控制 → Spring Security
- API → REST Controllers

## 六、核心文档使用场景

这些文档将贯穿整个开发过程:
